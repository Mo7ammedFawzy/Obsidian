# CH13 — Concurrency

## 1) Overview

Concurrency lets multiple tasks run at the same time. Java's high-level concurrency API (`java.util.concurrent`) sits atop the lower-level `Thread` / `synchronized` / `volatile` primitives. The exam emphasizes thread basics, the `ExecutorService`, futures, concurrent collections, atomic types, locks, race conditions/deadlocks, parallel streams, and (Java 21) **virtual threads**.

---

## 2) Key Concepts

### Threads

- A `Thread` is the unit of execution. Create one by:
  - Extending `Thread` and overriding `run`.
  - Implementing `Runnable` / `Callable` and passing to `new Thread(...)` or an executor.
- Lifecycle: `NEW → RUNNABLE → (BLOCKED|WAITING|TIMED_WAITING) → TERMINATED`.

### Virtual Threads (Java 21+)

- Lightweight threads scheduled by the JVM, **not** the OS.
- Created via `Thread.ofVirtual().start(...)` or `Executors.newVirtualThreadPerTaskExecutor()`.
- Ideal for I/O-bound workloads — millions can coexist.
- Platform threads remain the right fit for CPU-bound work.

### Executors and Thread Pools

`java.util.concurrent.Executors` factories:

| Factory | Description |
| --- | --- |
| `newSingleThreadExecutor()` | One worker, FIFO |
| `newFixedThreadPool(n)` | Fixed pool of `n` workers |
| `newCachedThreadPool()` | Grows/shrinks dynamically |
| `newScheduledThreadPool(n)` | For delayed/periodic tasks |
| `newVirtualThreadPerTaskExecutor()` | One virtual thread per task (Java 21) |

### Submitting Work

```java
ExecutorService es = Executors.newFixedThreadPool(2);
Future<Integer> f = es.submit(() -> 42);
Integer v = f.get();   // blocks until ready
es.shutdown();
```

- `submit(Runnable)` → `Future<?>`.
- `submit(Callable<T>)` → `Future<T>`.
- `invokeAll(...)` runs a list of `Callable`s and returns futures.
- `invokeAny(...)` returns the result of the first to succeed.

### Shutting Down

- `shutdown()` — stop accepting new tasks; finish queued ones.
- `shutdownNow()` — interrupt running tasks, return queued.
- `awaitTermination(timeout, unit)` — block until done.

### Concurrent Collections

| Class | Use case |
| --- | --- |
| `ConcurrentHashMap` | Thread-safe map; lock-striped |
| `CopyOnWriteArrayList` | Read-heavy lists |
| `ConcurrentLinkedQueue` | Lock-free FIFO |
| `BlockingQueue` (LinkedBlockingQueue, ArrayBlockingQueue) | Producer-consumer |
| `ConcurrentSkipListMap` | Sorted concurrent map |

### Synchronization Primitives

- `synchronized` blocks/methods → mutex on an object monitor.
- `volatile` field → visibility, no atomicity.
- `ReentrantLock` → explicit lock with `lock()` / `unlock()`.
- `ReadWriteLock` → many readers, one writer.
- `Semaphore` → permits.
- `CountDownLatch` → wait for N events.
- `CyclicBarrier` → rendezvous of N threads.

### Atomic Types

`AtomicInteger`, `AtomicLong`, `AtomicReference<T>` — non-blocking compare-and-set operations.

### Race Conditions, Deadlock, Livelock, Starvation

- **Race condition**: result depends on thread scheduling.
- **Deadlock**: two+ threads each waiting on a lock the other holds.
- **Livelock**: threads are active but make no progress (mutual yielding).
- **Starvation**: a thread never gets CPU/lock.

### Parallel Streams

- `collection.parallelStream()` or `stream().parallel()`.
- Backed by the **common `ForkJoinPool`** unless wrapped in a custom pool.
- Operations should be associative and stateless.

### CompletableFuture

- `supplyAsync`, `runAsync` — start async work.
- `thenApply`, `thenAccept`, `thenCompose`, `thenCombine` — chain.
- `exceptionally`, `handle` — error handling.
- `allOf`, `anyOf` — combinators.

## 3) Important Rules

- Calling `run()` directly on a `Thread` runs in the **current** thread; you must call `start()` to fork.
- A `Thread` cannot be `start()`ed twice — `IllegalThreadStateException`.
- `Thread.sleep` and `Object.wait` declare `InterruptedException`; you must catch or rethrow.
- `wait`, `notify`, and `notifyAll` must be called while **owning the monitor** (inside a `synchronized` block on the same object).
- `volatile` provides visibility (each read sees the latest write) but **not atomicity** — `i++` on a `volatile int` is still racy.
- `ExecutorService` must be **shut down**, otherwise the JVM may not exit (non-daemon threads).
- `Future.get()` blocks; `get(timeout, unit)` throws `TimeoutException` if exceeded.
- `Callable.call()` may throw checked exceptions; `Runnable.run()` cannot.
- `parallelStream()` does **not** guarantee order unless terminal op preserves encounter order.
- Concurrent collections do **not** throw `ConcurrentModificationException` — they iterate over a weakly-consistent or snapshot view.
- `synchronized` is **reentrant**: the same thread can re-acquire a lock it already holds.
- Locks acquired via `ReentrantLock` must be released in `finally`; otherwise a thrown exception leaves the lock held.
- `CountDownLatch` is one-shot; `CyclicBarrier` resets after each cycle.
- Atomic operations (`compareAndSet`) replace `synchronized` for simple counters / flags with much lower overhead.
- Virtual threads are **always daemons** by default and don't prevent JVM exit on their own.

## 4) Code Examples

### Simple thread

```java
Thread t = new Thread(() -> System.out.println("hi"));
t.start();
t.join();
```

### Executor with `Future`

```java
try (ExecutorService es = Executors.newFixedThreadPool(2)) {
    Future<Integer> f = es.submit(() -> 1 + 2);
    System.out.println(f.get());     // 3
}   // try-with-resources calls close() = shutdown + awaitTermination
```

### `ConcurrentHashMap` atomic update

```java
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge("hits", 1, Integer::sum);   // atomic
```

### Producer-consumer with `BlockingQueue`

```java
BlockingQueue<String> q = new LinkedBlockingQueue<>(10);

Runnable producer = () -> {
    try { q.put("hello"); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};
Runnable consumer = () -> {
    try { System.out.println(q.take()); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};
```

### `CompletableFuture` chain

```java
CompletableFuture
    .supplyAsync(() -> fetchUser(id))
    .thenApplyAsync(user -> fetchOrders(user))
    .thenAccept(orders -> render(orders))
    .exceptionally(ex -> { log(ex); return null; });
```

### Virtual threads (Java 21)

```java
try (ExecutorService es = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
        es.submit(() -> Thread.sleep(Duration.ofMillis(100))));
}
```

### Tricky: deadlock

```java
synchronized (a) {
    synchronized (b) { ... }
}
// Thread 2:
synchronized (b) {
    synchronized (a) { ... }      // ⇒ potential deadlock
}
```

### Tricky: `volatile` is NOT atomic

```java
volatile int counter;
// 1000 threads doing counter++ → still gets racy results
// Use AtomicInteger or synchronized
```

### `Atomic` for counters

```java
AtomicInteger n = new AtomicInteger();
n.incrementAndGet();
n.compareAndSet(1, 2);
```

## 5) Common Mistakes

- ❌ Calling `run()` instead of `start()` — runs synchronously, no concurrency.
- ❌ Forgetting to shut down an `ExecutorService` — JVM doesn't exit.
- ❌ Treating `volatile` as atomic for compound operations.
- ❌ Using `HashMap` from multiple threads — corruption (infinite loops in old JDKs).
- ❌ `wait`/`notify` outside `synchronized` → `IllegalMonitorStateException`.
- ❌ Holding a `ReentrantLock` without `try { ... } finally { lock.unlock(); }`.
- ❌ Using parallel streams for I/O — they share the common `ForkJoinPool` and starve other tasks.
- ❌ Believing virtual threads make CPU-bound work faster — they don't; pin to platform threads instead.
- ❌ Mutating shared state inside a parallel stream pipeline.
- ❌ Calling `Thread.start()` twice on the same thread.

## 6) Mental Model

Java concurrency layers:

1. **Threads** are the engine; you can build everything on them but rarely should.
2. **Executors** decouple task submission from thread management.
3. **Concurrent collections / atomics** are pre-built thread-safe data structures.
4. **High-level coordinators** (`CountDownLatch`, `Semaphore`, `CompletableFuture`) handle common patterns.
5. **Virtual threads** dramatically widen the design space for I/O concurrency in Java 21+.

For correctness, pick the **smallest tool** that solves your problem:
- Single counter? `AtomicInteger`.
- Read-heavy map? `ConcurrentHashMap`.
- Producer/consumer? `BlockingQueue`.
- One-time wait? `CountDownLatch`.
- Repeated barrier? `CyclicBarrier`.
- Async chain? `CompletableFuture`.
- Massive I/O fan-out? Virtual threads.

Race conditions arise from *unprotected shared state*. Choose between immutability (best), confinement (per-thread), and synchronization (last resort).

---

## 7) Quick Revision

- `start()` forks; `run()` doesn't.
- `volatile` ≠ atomic.
- Always shut down executors.
- `Callable` can throw checked; `Runnable` cannot.
- Concurrent collections never throw CME but offer weak consistency.
- Virtual threads ≈ many cheap threads for blocking I/O (Java 21).
- `wait/notify` require holding the monitor.
- `CountDownLatch` is one-shot; `CyclicBarrier` resets.
- Parallel streams use the **common ForkJoinPool** by default.
- Prefer `CompletableFuture` over manual thread chaining for async pipelines.
